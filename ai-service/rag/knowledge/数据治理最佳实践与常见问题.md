# 数据治理最佳实践与常见问题

本文档汇总数据质量治理中的最佳实践、常见陷阱和解决方案，帮助 AI 更准确地生成规则。

---

## 一、规则设计最佳实践

### 1.1 从业务出发，而非从技术出发
- 先理解业务含义，再选择规则类型
- 例如：同样是数字字段，"年龄"用 RANGE（0~150），"手机号"用 REGEX（格式校验）
- 字段名可能不直观，要结合 comment（备注）判断真实业务含义

### 1.2 最小够用原则
- 不要过度校验：只为关键业务字段设置规则
- 对于 description、remark 等非关键字段，通常只需 LENGTH 限制
- 避免对同一字段设置过多冗余规则

### 1.3 规则粒度：一条规则解决一个问题
- 每条规则只校验一个维度的质量问题
- 例如：手机号需要3条规则（非空 + 唯一 + 格式），而不是试图用一条规则覆盖所有

### 1.4 规则命名规范
- 使用 `{表名/字段名}+{规则类型}+校验` 的命名方式
- 好的命名：`用户手机号非空校验`、`订单金额范围校验`
- 差的命名：`规则1`、`test`、`check`

## 二、常见业务领域的规则重点

### 2.1 电商领域
- **商品表**：价格>0、库存>=0、SKU唯一、名称非空
- **订单表**：订单号唯一、金额>0、状态枚举、收货地址长度
- **用户表**：手机号格式+唯一、用户名长度、邮箱格式

### 2.2 金融领域
- **账户表**：账户号唯一、余额>=0、状态枚举
- **交易表**：交易流水号唯一、金额>0、交易时间非空
- **风控表**：评分范围、风险等级枚举

### 2.3 人力资源领域
- **员工表**：工号唯一、姓名非空、手机号格式、入职日期非空
- **考勤表**：打卡时间非空、工时范围（0~24）
- **薪资表**：薪资>0、发放月份格式

### 2.4 医疗领域
- **患者表**：身份证号格式+唯一、姓名非空、年龄范围
- **处方表**：药品编码非空、剂量>0、处方日期非空
- **诊断表**：ICD编码格式、诊断描述非空

### 2.5 教育领域
- **学生表**：学号唯一、姓名非空、年龄范围、性别枚举
- **课程表**：课程编码唯一、学分>0、课时>0
- **成绩表**：分数范围（0~100或0~150）、学生ID非空

## 三、常见陷阱与规避

### 3.1 陷阱：用 LENGTH 校验数值字段
- **错误**：对 INT 类型的 age 字段设置 LENGTH 规则
- **正确**：对 age 使用 RANGE 规则（min=0, max=150）
- **原因**：LENGTH 是校验字符串字符数的，不适用于数值

### 3.2 陷阱：ENUM 值类型不匹配
- **错误**：TINYINT 类型的 status 字段，ENUM values 写成 ["启用", "禁用"]
- **正确**：ENUM values 写成 ["0", "1"]，与数据库实际存储值一致
- **原因**：ENUM 校验的是数据库中的实际存储值，不是前端显示值

### 3.3 陷阱：REGEX 忘记锚定首尾
- **错误**：pattern 写成 `1[3-9]\d{9}`（无锚定）
- **正确**：pattern 写成 `^1[3-9]\d{9}$`（加 ^ 和 $）
- **原因**：不加锚定会导致部分匹配也通过（如 "abc13800138000xyz"）

### 3.4 陷阱：RANGE 边界值处理
- **问题**：金额字段 RANGE min=0 时，0 也算合法值
- **建议**：金额字段通常用 min=0.01 排除零值
- **注意**：库存字段用 min=0（允许零库存）

### 3.5 陷阱：UNIQUE 对 NULL 的处理
- **事实**：MySQL 中 UNIQUE 约束允许多个 NULL 值
- **建议**：如果字段既要唯一又不允许空，需同时配置 UNIQUE + NOT_NULL

### 3.6 陷阱：忽略字段的数据类型
- **错误**：对 DATETIME 类型字段用 REGEX 校验日期格式
- **正确**：对 DATETIME 字段用 RANGE 校验日期范围，或只配 NOT_NULL
- **原因**：日期类型在数据库中已有格式保证，不需要正则校验

## 四、用户描述的关键词映射

以下是用户自然语言中常见的关键词与规则类型的映射：

| 用户可能说的关键词 | 对应规则类型 | 示例 |
|-----------------|-----------|------|
| 不能为空、必填、非空、不允许空值 | NOT_NULL | "用户名不能为空" |
| 不能重复、唯一、不可重复、去重 | UNIQUE | "手机号不能重复" |
| 长度、字数、字符数、N个字以内 | LENGTH | "名称不超过20个字" |
| 范围、大小、大于、小于、不超过 | RANGE | "年龄在18到60之间" |
| 格式、正则、手机号格式、邮箱格式 | REGEX | "手机号格式校验" |
| 只能是、只能是...之一、枚举、固定值 | ENUM | "性别只能是男或女" |
| 跨表、关联、一致性、汇总 | CUSTOM_SQL | "订单金额要等于明细之和" |

## 六、规则生成的质量检查清单

生成规则后，应按以下清单自检：

1. ✅ **字段名存在性**：column 值是否是提供的字段列表中实际存在的字段名？
2. ✅ **规则类型正确性**：ruleType 是否是 7 种合法类型之一？
3. ✅ **ruleConfig 格式**：ruleConfig 是否是 JSON 对象（不是字符串）？
4. ✅ **字段类型匹配**：LENGTH 是否用于字符串字段？RANGE 是否用于数值字段？
5. ✅ **业务语义合理**：规则是否符合用户描述的业务需求？
6. ✅ **命名清晰**：ruleName 是否简洁明了地描述了规则用途？
7. ✅ **描述完整**：description 是否清楚说明了校验逻辑？
